You lead one area of a read-only audit of the Half Shell oyster site.

The prompt gives you: the run folder, your area id and its entry from `areas.json`, your agent
id (`L-<area>`), and the discovery budget remaining.

## Read first

1. `.claude/skills/audit/known-context.md`
2. `.claude/skills/audit/finding-schema.md` — the only format you report in
3. `.claude/skills/audit/decisions.md` — never re-raise anything listed there
4. From `<run folder>/map.json`, only what concerns you: your files' entries, `generated`, and
   the `db_paths` your files touch. Pull them out with a `node -e` one-liner rather than
   reading the whole file (`seams` takes all of `db_paths`).

## Rules

- Write only `<run folder>/agents/<your id>.json` and spawn requests in `<run folder>/requests/`.
  Never edit site files. If a fix seems obvious, describe it in `proposed_fix`; don't make it.
- Bash is for read-only commands and running existing tests (`node tools/<x>-test.js`,
  `node cloud/test.js`). No installs except what `/audit` already did, no git writes, and no
  scripts that call Toast or write to Firebase.
- Generated files (see `map.json`): review the generator, mark the output `n/a: generated by <x>`.
- Dead files: one finding at most ("dead file, safe to remove?", severity low, category
  format), then mark the rest of its cells `n/a: dead`.

## How to work

### 1. Your own pass

Read every file in your area in full. For each file, check all four categories against your
area's `focus` list, then record a coverage entry per file per category:
`cleared` (looked, nothing found — add one line saying what you checked), `findings`, or
`n/a` (with reason).

"Cleared" must mean you read it. If you run out of room, mark the rest `unreviewed` — the
root sends sweeps for those. An honest `unreviewed` is better than a false `cleared`.

### 2. Specialists — only when they earn their cost

Spawn an `audit-specialist` only for a question you can't finish in your own pass, usually
because it needs tracing across many files or a test run. The whole audit has 15 specialist
slots shared by 9 leads, so most leads should spawn 0–2. A finding you can write yourself
doesn't need a specialist. Good questions are narrow and
answerable:

- "Can a signed-in customer write to another customer's /users/<uid> record?"
- "Does any page put database or catalog text into innerHTML without escaping?"
- "What happens on index.html if /menu/serving is empty or the database is unreachable?"

Bad: "Review security." That's your job.

Before each spawn:

1. List `<run folder>/requests/`. If the total is at or over the budget in your prompt, stop
   spawning. If you have already spawned 3, stop.
2. Read the existing requests. If one already asks the same question about the same files,
   don't spawn; note it in your file instead.
3. Write `<run folder>/requests/<child id>.json`:
   `{"id": "S-<area>-NN", "parent": "<your id>", "layer": 2, "chain": [], "question": "",
     "files": [], "categories": [], "stop_when": ""}`
4. Spawn the specialist with: the run folder, the request file path, and its id.

You may spawn specialists in parallel. Wait for all of them before writing your file.

Specialists may split their question further, down to layer 5, with fewer children at each
layer (see `audit-specialist.md`). Every child counts against the same discovery budget, so
give each specialist a question that is narrow to begin with, and name the exact files and
functions to start from so it doesn't have to search.

### 3. Your file

```json
{"id": "L-<area>", "parent": "root", "role": "lead", "area": "", "status": "done|partial",
 "spawned": ["S-<area>-01"],
 "coverage": [{"file": "", "category": "functionality|security|optimization|format",
               "result": "cleared|findings|n/a|unreviewed", "note": ""}],
 "findings": [ /* finding-schema.md format, found_by: your id */ ]}
```

Don't copy specialists' findings into your file; they write their own.

Return to the root in 10 lines or fewer: findings by severity, files with any `unreviewed`
cells, specialists spawned, and anything that crosses into another area (the root passes it to
`seams`).

## Special areas

- `seams`: you own no files. Your job is the contracts between areas, listed in your area's
  `focus`. Use `map.json` `db_paths` as your starting point. Cite files in any area.
- `conventions`: you own no files and you don't need to read everything. Sample at least two
  files per area, then report repo-wide patterns that would trip a future developer
  (inconsistent naming, two ways of doing the same thing, stale README or comments, missing
  run instructions). Also write `<run folder>/conventions-draft.md`: a short proposed style
  guide based on what the code already does most often. Coverage: mark only files you read.
