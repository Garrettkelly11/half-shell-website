# Known context for auditors

Facts about how the Half Shell site works. Check findings against these before reporting.
If the code contradicts one of these, that contradiction is itself worth reporting.

## How it runs

- **Hosting:** GitHub Pages, served from the root of `main`. No build step. A push to `main` is
  a production deploy. No agent ever commits or pushes.
- **Live menu data:** `.github/workflows/sync-oysters.yml` runs `tools/sync-toast-to-firebase.js`
  on a schedule. It writes the in-stock list to the Realtime Database at `/menu/serving`.
  Pages read it with the Firebase JS SDK.
- **Older sync path:** `sync.js` writes `public/oysters.json`. The README still describes it.
  The scout should confirm whether anything still reads `public/oysters.json`.
- **`functions/`** is mostly legacy. Its Firebase Functions are not deployed. But
  `functions/toast-mapping.js` IS live: the sync script requires it for Toast GUID overrides.
- **`cloud/`** is the current Cloud Functions codebase (startToastSync, setMenuOverride,
  setHappyHour, deletePassport). It deploys only with `firebase deploy --only functions:cloud`.
  A bare `firebase deploy` would also publish the legacy config in `firebase.json`; never
  suggest running it.
- **Customers** sign in with phone numbers (Oyster Passport). **Staff** are users listed
  under `/staff/<uid>` in the database.

## Running code during the audit

The audit runs in Garrett's working copy, which has real Toast credentials in `.env` and
may have Firebase admin credentials set on the machine. So:

- Never read `.env` or `functions/.env`. `.env.example` files are fine.
- Never run `tools/toast-*.js`, `tools/sync-toast-to-firebase.js`, `sync.js`, or anything in
  `functions/`. They call Toast or write to the live database. Read them; don't run them.
- Never run `firebase`, `gcloud`, or any git command that changes files or history.
- Fine to run: `node cloud/test.js`, `node tools/*-test.js`, `node -e` one-liners that read
  files, and verifier scratch scripts under `audit/runs/<run-id>/scratch/` that call pure
  logic only.
- The working copy may contain Garrett's uncommitted work. Audit it as it is; never revert,
  restore or "clean up" anything.

## Things that look like bugs but aren't

- **The Firebase web config in `src/firebase-config.js` (apiKey etc.) is public by design.**
  Every Firebase web app ships it. Security comes from `database.rules.json`, Auth, and the
  cloud functions' own checks. Don't report the key. Do report anything that relies on the
  key being secret.
- **Generated files:** `data/oysters.js` and `data/regions.js` are written by Merroir (the
  staff app) after the catalog switch-over. Don't propose hand edits; propose changes to the
  editor or the schema checks instead. The catalog's contents (tasting notes, farm names)
  are out of scope; its structure and parsing are in scope. `Oyster Overview.html` is
  generated by `tools/build-library.js`, and `data/map-na.js` by `tools/build-map-na.js`.
  Review the generators.
- **86 status** means "not currently offered", not "out of stock". An 86'd oyster missing from
  the menu is correct.
- **`.env.example` files** hold placeholders, not secrets.

## Known open items (report status, don't rediscover)

- As of September 2026, the digital menu had no posted shellfish consumer advisory, which
  North Carolina requires. Check whether it is still missing and report it once, under
  `public-menu`, with severity high if missing.

## House rules that affect proposed fixes

- Every change to the site is logged in `Changelog.md`, which is kept outside this repo. Fixers
  handle that later; auditors just note it in `proposed_fix` when a fix touches site behaviour.
- Examples that show a person's name use **Jane Doe** (username `Jane.D`, display `Jane D.`),
  never a real staff member's name.
