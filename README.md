# Half Shell — Raw Bar Digital Menu

Digital menu website for **Half Shell**, Charlotte's raw bar. Displays nightly oyster selections with flavor profiles, origins, and pricing.

**Live site:** https://hsoysters.com

---

## Pages

| File | Purpose |
|---|---|
| `landing.html` | What the QR code opens: pick the Oyster Menu or the Bar Menu (the Bar choice stays hidden until `config/drinksPublic` is true) |
| `index.html` | Tonight's oyster menu (customer-facing) |
| `bar.html` | The bar (drinks) menu, its own dark page with no link to the oyster menu, library or Passport. Guests are sent to the front page until `config/drinksPublic` is true; signed-in staff can preview it |
| `curated-flights.html` | Curated Flights, built from tonight's menu |
| `oyster.html` | One oyster's full profile (`oyster.html?id=<id>`) |
| `Oyster Overview.html` | Oyster Library, every catalog oyster (generated) |
| `passport.html` | Oyster Passport for signed-in guests |
| `user.html` | Oyster Passport sign-up and sign-in |
| `privacy.html` | Privacy notice |
| `employee.html` | Staff page: menu overrides, happy hour, catalog editing, and (managers) the Drinks and Specials tabs |
| `wifi.html` | Only redirects to `landing.html`, so an old captive-portal URL or QR keeps working. Delete it once UniFi points at `landing.html` |

## Data

- `data/oysters.js`, `data/regions.js` — the oyster catalog. Edited by hand until the Merroir switch-over; after that, managers edit it on the employee page's Oysters tab and Merroir commits these files (first line: "Generated by Merroir — do not edit by hand"). Don't edit them by hand then.
- `Oyster Overview.html` — the library page, generated by `tools/build-library.js`; `.github/workflows/build-library.yml` rebuilds it when the catalog changes on `main`

## Bar menu, drink specials and the nightly specials sheet

- **Toast owns the drinks** (Data Ownership Map): a drink's name, price (or glass/bottle sizes), section, order and 86 status come from the Toast Drinks menu. The Toast sync (`tools/sync-toast-to-firebase.js`, every 15 minutes) copies every Drinks item to `menu/toastDrinks/{key}` (key = the name with letters and numbers only, accents and the DFT/CAN/BTL prefix dropped: `toastKey` in `src/drinks-core.js`). Managers never enter a price or section. They add only the extras (description, photo, tags, allergens, ABV, size note) on a record in `menu/drinks`, and a drink **appears on the bar menu once a manager adds it** (and while Toast does not have it 86'd); the record adds its extras. **Managers choose what shows**: the Drinks tab lists every Toast drink (so Coke or the corking fee never appear unless someone adds them); Add to menu / Take off menu per drink, per section, or for ticked drinks (`setOnMenu`), or import a csv of names. A record is what puts a drink on the menu; its details are optional extras. A record with no Toast drink never shows. Price specials are display only (set the matching discount in Toast too), apply to single-priced drinks, and must be under the Toast price. A limited-time special has no price or name of its own: it only makes an existing drink show during its window.
- **Data** (Realtime Database): `menu/toastDrinks` (from the sync; staff, or everyone once public), `menu/drinks`, `menu/drinkSpecials`, `menu/nightlySpecials/{date}` (staff only; that night's food specials in menu order, never shown to guests), `menu/specialsLibrary/{id}` (staff only; every food special a manager has saved, to pick from another night), `config/drinksPublic`. Browsers never write them: the managers' tabs call Cloud Functions (`saveDrink`, `removeDrink`, `importDrinks`, `saveSpecial`, `removeSpecial`, `saveNightly`, `saveLibrarySpecial`, `removeLibrarySpecial`, `uploadDrinkPhoto` in `cloud/drinks-lib.js`), which check the manager rank, validate again and write an audit-log entry.
- **Logic**: `src/drinks-core.js` (validation, csv import, specials schedules, the guest menu), shared by `bar.html`, the manager tabs and the functions (`cloud/vendor-site.js` copies it into `cloud/site/` on deploy). `src/drinks-xlsx.js` reads `.xlsx` files with no library. `src/drinks-admin.js` and `.css` are the Drinks and Specials tabs.
- **Food specials menu (Specials tab)**: create a special (saved to the list), build tonight's list from the saved list, reorder it (drag or arrows), save, and export a PDF. `src/specials-pdf.js` lays out one US Letter sheet with two identical 4.25" x 11" menus to cut down the middle (Olivero-style run-in items, Playfair Display and Lato, centred, NC shellfish advisory at the foot). It uses pdf-lib and fontkit from `src/vendor/` and the fonts in `assets/fonts/`, loaded only when a manager exports.
- **Not public yet**: `database.rules.json` lets only staff read `menu/toastDrinks`, `menu/drinks` and `menu/drinkSpecials` until `config/drinksPublic` is `true`. After the owners approve, set that one value to `true` in the Firebase console (Realtime Database, `config`). Set it back to `false` to hide the bar menu again. Photos are saved in Firebase Storage (`storage.rules`: links open, folder can't be listed, browsers can't write).
- **Deploying it** (one time): enable Storage in the Firebase console, then `firebase deploy --only functions:cloud,database,storage`. Nothing changes for guests until the flag is flipped. The bar menu stays empty until the first Toast sync after the deploy has written `menu/toastDrinks` (run "Sync Toast" on the employee page or the Action by hand; `node tools/sync-toast-to-firebase.js --dry-run` shows the Drinks count first).

## Toast API Sync

`tools/sync-toast-to-firebase.js` polls the Toast Menus API and writes the in-stock oyster list to the Firebase Realtime Database at `/menu/serving`. The menu pages read it live with the Firebase JS SDK. The sync runs automatically via `.github/workflows/sync-oysters.yml` every 15 minutes.

### Setup (one-time)

1. Purchase Toast Standard API Access from the Toast Shop
2. Add four secrets to your GitHub repo (Settings → Secrets and variables → Actions):
   - `TOAST_CLIENT_ID`
   - `TOAST_CLIENT_SECRET`
   - `TOAST_RESTAURANT_GUID`
   - `FIREBASE_ADMIN_CREDENTIALS` — the full JSON of a Firebase service account key
     (paste the file's contents, not its path)
3. The workflow in `.github/workflows/sync-oysters.yml` handles the rest automatically.
